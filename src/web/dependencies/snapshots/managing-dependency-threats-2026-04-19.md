hx-flex hx-gap-4 hx-font-mono hx-tracking-tight hx-whitespace-nowrap"><div>December 10, 2025</div><div>|</div><div>Updated <time datetime=2026-04-09T11:39:06.000Z>April 9, 2026</time></div></div></div><h2>Scenario overview<span class="hx-absolute -hx-mt-20" id=scenario-overview></span>
<a href=#scenario-overview class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>Modern software development relies heavily on dependencies - third-party packages, libraries, and modules that accelerate development but also introduce security risks. Supply chain attacks targeting dependencies have become increasingly sophisticated, with malicious actors using techniques like typosquatting, package confusion, package hijacking, account takeovers, and injecting malicious code into legitimate packages.</p><p>One example is <a href=https://socket.dev/blog/ongoing-supply-chain-attack-targets-crowdstrike-npm-packages target=_blank rel=noopener>Shai-Hulud</a>, a self-replicating worm that infiltrated the npm ecosystem via compromised maintainer accounts, injecting malicious post-install scripts into popular JavaScript packages. The malware also stole credentials, injected backdoors, and attempted to destroy the user&rsquo;s home directory.</p><p>Managing dependency threats requires a defense-in-depth strategy. No single control is perfect. Even registry-level protections like package cooldown periods (waiting periods after unpublishing before names can be re-registered) aren&rsquo;t sufficient against determined attackers. Layering multiple defenses creates a more robust security posture. This article provides opinionated guidance on implementing practical security measures that have been field-tested against real-world attacks like Shai-Hulud.</p><h2>Key design strategies<span class="hx-absolute -hx-mt-20" id=key-design-strategies></span>
<a href=#key-design-strategies class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>Layered defenses reduce single points of failure by using multiple controls that reinforce each other - each covers gaps the others leave, so together they form a complete defense. Implement these core strategies:</p><ol><li><strong>Disable package lifecycle scripts by default</strong>: Package managers execute scripts automatically during installation (<code>preinstall</code>, <code>postinstall</code>, etc.). These scripts can run arbitrary code on your system before you&rsquo;ve reviewed the package contents. Disabling them by default prevents the most common attack vector.</li><li><strong>Use dev containers for isolation</strong>: Development containers provide strong isolation between host machine and project environment. Even if malicious code executes, it can&rsquo;t access the actual home directory, SSH keys, or cloud credentials. GitHub Codespaces and Windows 365 provide managed environments with isolation built in.</li><li><strong>Require signed commits with user interaction</strong>: Cryptographic commit signing with biometric or password authentication prevents malicious scripts from creating commits without your knowledge. Tune alerts to reduce fatigue and establish response runbooks.</li></ol><p><strong>Implementation checklist:</strong></p><ul><li><input disabled type=checkbox> Configure package managers to disable lifecycle scripts by default</li><li><input disabled type=checkbox> Always use lockfiles for ecosystems that support them to ensure deterministic builds</li><li><input disabled type=checkbox> Use dev containers for development, especially for untrusted code</li><li><input disabled type=checkbox> Enable commit signing with user interaction (passphrase, biometric, or hardware key)</li><li><input disabled type=checkbox> Configure repository rulesets requiring pull requests and status checks</li><li><input disabled type=checkbox> Enable Dependabot alerts and security updates for all repositories</li><li><input disabled type=checkbox> Configure dependency review action as a required status check on pull requests</li><li><input disabled type=checkbox> Enable code scanning with CodeQL or third-party tools; <a href=#configure-commit-signing class=subheading-anchor aria-label="Permalink for this section"></a></h4><p><a href=https://docs.github.com/en/authentication/managing-commit-signature-verification/signing-commits target=_blank rel=noopener>Configure commit signing using a GPG, SSH, or S/MIME key</a>. For maximum protection against automated attacks, use a signing method that requires user interaction. Examples include using a passphrase-protected key, biometric authentication, or a hardware security key.</p><div class="hx-overflow-x-auto hx-mt-6 hx-flex hx-rounded-lg hx-border hx-py-2 ltr:hx-pr-4 rtl:hx-pl-4 contrast-more:hx-border-current contrast-more:dark:hx-border-current hx-border-blue-200 hx-bg-blue-100 hx-text-blue-900 dark:hx-border-blue-200/30 dark:hx-bg-blue-900/30 dark:hx-text-blue-200"><div class="ltr:hx-pl-3 ltr:hx-pr-2 rtl:hx-pr-3 rtl:hx-pl-2"><div class="hx-select-none hx-text-xl" style="font-family:apple color emoji,segoe ui emoji,segoe ui symbol">ℹ️</div></div><div class="hx-w-full hx-min-w-0 hx-leading-7"><div class="hx-mt-6 hx-leading-7 first:hx-mt-0"><strong>Why user interaction matters:</strong> The key defense here isn&rsquo;t just the cryptographic signature - it&rsquo;s the human verification step. A malicious script running on your machine can access your signing key, but it can&rsquo;t press your fingerprint to the sensor or type your passphrase. This human-in-the-loop requirement is what blocks automated attacks from creating commits on your behalf.</div></div></div><p>Commit signing can be enforced via repository rulesets. See <a href=#layer-4-enforce-repository-rulesets>Layer 4: Enforce repository rulesets</a> for configuration details.</p><p>GitHub provides <a href=https://docs.github.com/enterprise-cloud@latest/authentication/managing-commit-signature-verification/signing-commits target=_blank rel=noopener>additional documentation on configuring commit signing</a>.</p><h3>Layer 4: Enforce repository rulesets<span class="hx-absolute -hx-mt-20" id=layer-4-enforce-repository-rulesets></span>
<a href=#layer-4-enforce-repository-rulesets class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>This defense layer happens at the repository level. Rulesets ensure that no code reaches your default branch without going through review and automated security checks.</p><h4>Configure rulesets<span class="hx-absolute -hx-mt-20" id=configure-rulesets></span>
<a href=#configure-rulesets class=subheading-anchor aria-label="Permalink for this section"></a></h4><p>Create a ruleset for your default branch:</p><ol><li>Navigate to <strong>Settings</strong> → <strong>Rules</strong> → <strong>Rulesets</strong></li><li>Add a new ruleset targeting your default branch</li><li>Examples of <a href=https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets target=_blank rel=noopener>protection rules</a> to configure:<ul><li>Require pull requests before merging</li><li>Require signed commits</li><li>Require status checks to pass (including security scans)</li><li>Require at least one approver (preferably two for critical repositories)</li><li>Require re-review when new commits are pushed</li><li>Require review from someone other than the last pusher</li><li>Require code scanning results</li><li>Do not allow bypassing of pull request requirements</li></ul></li></ol><h3>Layer 5: Establish trusted publishing and verification<span class="hx-absolute -hx-mt-20" id=layer-5-establish-trusted-publishing-and-verification></span>
<a href=#layer-5-establish-trusted-publishing-and-verification class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Build trust across the supply chain by establishing cryptographic provenance for packages. This layer works both directions: publishers create trustworthy artifacts, and consumers verify them.</p><h4>For package publishers: Configure trusted publishing<span class="hx-absolute -hx-mt-20" id=for-package-publishers-configure-trusted-publishing></span>
<a href=#for-package-publishers-configure-trusted-publishing class=subheading-anchor aria-label="Permalink for this section"></a></h4><p><a href=https://docs.npmjs.com/trusted-publishers target=_blank rel=noopener>Trusted publishing</a> removes the need to manage long-lived API tokens in your build systems. Instead, your CI/CD pipeline attests the build artifacts and uses OIDC to authenticate directly with package registries. This achieves <a href=https://slsa.dev/spec/v1.0/levels#build-l3 target=_blank rel=noopener>SLSA Build Level 3</a> security and enables code-to-cloud traceability, and eliminates the risk of stolen tokens being used to publish malicious versions.</p><p>For packages you maintain:</p><ol><li>Link your GitHub repository as a trusted publisher in your package registry settings (npm, PyPI, RubyGems, NuGet, crates.io, etc.)</li><li>Update your release workflow to use <a href=https://docs.github.com/en/actions/how-tos/secure-your-work/security-harden-deployments target=_blank rel=noopener>OIDC authentication</a> instead of long-lived tokens</li><li>Publish with provenance attestations (e.g., <code>npm publish --provenance</code>) to create cryptographic proof on the specific commit of the source repository</li><li>Create <a href=https://docs.github.com/enterprise-cloud@latest/code-security/concepts/supply-chain-security/linked-artifacts target=_blank rel=noopener>linked artifact storage records</a> with the <a href=https://github.com/actions/attest target=_blank rel=noopener><code>actions/attest</code></a> action</li></ol><h4>For package consumers: Validate package attestations<span class="hx-absolute -hx-mt-20" id=for-package-consumers-validate-package-attestations></span>
<a href=#for-package-consumers-validate-package-attestations class=subheading-anchor aria-label="Permalink for this section"></a></h4><p><a href=https://docs.npmjs.com/viewing-package-provenance target=_blank rel=noopener>Package attestations</a> provide cryptographic proof of a package&rsquo;s provenance, verifying it was built from specific source code through a verified build process. When consuming packages, validate that they come from trusted publishers.</p><p>For packages you depend on:</p><ol><li>Use <code>npm audit signatures</code> to verify packages have valid attestations and signatures, identifying the source repository and commit</li><li>Integrate attestation validation into your CI/CD pipeline for continuous verification</li><li>Prioritize dependencies published with attestations in your dependency selection decisions</li></ol><div class="hx-overflow-x-auto hx-mt-6 hx-flex hx-rounded-lg hx-border hx-py-2 ltr:hx-pr-4 rtl:hx-pl-4 contrast-more:hx-border-current contrast-more:dark:hx-border-current hx-border-blue-200 hx-bg-blue-100 hx-text-blue-900 dark:hx-border-blue-200/30 dark:hx-bg-blue-900/30 dark:hx-text-blue-200"><div class="ltr:hx-pl-3 ltr:hx-pr-2 rtl:hx-pr-3 rtl:hx-pl-2"><div class="hx-select-none hx-text-xl" style="font-family:apple color emoji,segoe ui emoji,segoe ui symbol">ℹ️</div></div><div class="hx-w-full hx-min-w-0 hx-leading-7"><div class="hx-mt-6 hx-leading-7 first:hx-mt-0">Yarn does not yet support a command for validating package attestations. There is an <a href=https://github.com/yarnpkg/berry/issues/6487 target=_blank rel=noopener>open issue</a> tracking this feature request.</div></div></div><h3>Layer 6: Monitor and respond continuously<span class="hx-absolute -hx-mt-20" id=layer-6-monitor-and-respond-continuously></span>
<a href=#layer-6-monitor-and-respond-continuously class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Automate vulnerability detection and establish processes for responding to security alerts. The goal is visibility into your dependency risk without overwhelming your team with noise.</p><h4>Configure automated scanning<span class="hx-absolute -hx-mt-20" id=configure-automated-scanning></span>
<a href=#configure-automated-scanning class=subheading-anchor aria-label="Permalink for this section"></a></h4><p>Build a comprehensive automated detection system that catches vulnerabilities at multiple stages:</p><p><strong>Dependency vulnerabilities:</strong></p><p>Enable <a href=https://docs.github.com/enterprise-cloud@latest/code-security/dependabot/dependabot-security-updates/about-dependabot-security-updates target=_blank rel=noopener>Dependabot security updates</a> to automatically detect vulnerabilities and create pull requests for updates. Consider grouping patch updates for expedited review, assigning security team reviewers, and scheduling daily scans. Use <a href=https://docs.github.com/enterprise-cloud@latest/code-security/dependabot/dependabot-auto-triage-rules/about-dependabot-auto-triage-rules target=_blank rel=noopener>auto-triage rules</a> to reduce alert fatigue by automatically dismissing low-risk alerts or alerts for dependencies that don&rsquo;t affect your usage. For comprehensive guidance on managing security alerts at scale, see <a href=../prioritizing-alerts/>Prioritizing security alert remediation</a>.</p><p>Add the <a href=https://github.com/actions/dependency-review-action target=_blank rel=noopener>dependency review action</a> to your pull request workflows and require it as a status check to prevent potential vulnerabilities from being introduced. Configure it to fail on high-severity vulnerabilities, block problematic licenses, and warn on low <a href=https://securityscorecards.dev/ target=_blank rel=noopener>OpenSSF Scorecard</a> scores.</p><p><strong>Code vulnerabilities and secrets:</strong></p><p>Enable <a href=https://docs.github.com/enterprise-cloud@latest/code-security/code-scanning/introduction-to-code-scanning/about-code-scanning target=_blank rel=noopener>code scanning</a> to detect vulnerabilities and coding errors in your source code. Configure CodeQL or third-party tools to run on pull requests and block merges when issues are found.</p><p>Enable <a href=https://docs.github.com/enterprise-cloud@latest/code-security/secret-scanning/introduction/about-secret-scanning target=_blank rel=noopener>secret scanning</a> to detect accidentally committed credentials. Configure push protection to prevent secrets from being pushed in the first place, and establish a response runbook for when alerts are triggered.</p><p><strong>Prioritize alerts with production context:</strong></p><p>If you track your builds as <a href=https://docs.github.com/enterprise-cloud@latest/code-security/concepts/supply-chain-security/linked-artifacts target=_blank rel=noopener>linked artifacts</a> with deployment records, you can filter Dependabot and code scanning alerts based on what&rsquo;s actually deployed in production. Use filters like <code>has:deployment</code> and <code>runtime-risk</code> alongside EPSS and CVSS scores to <a href=https://docs.github.com/enterprise-cloud@latest/code-security/tutorials/secure-your-organization/prioritize-alerts-in-production-code target=_blank rel=noopener>focus remediation on vulnerabilities that pose real risk</a> to your running systems.</p><h4>Review dependency updates systematically<span class="hx-absolute -hx-mt-20" id=review-dependency-updates-systematically></span>
<a href=#review-dependency-updates-systematically class=subheading-anchor aria-label="Permalink for this section"></a></h4><p>Beyond automated tooling, establish a human review process for evaluating dependency changes:</p><div class="hx-overflow-x-auto hx-mt-6 hx-flex hx-rounded-lg hx-border hx-py-2 ltr:hx-pr-4 rtl:hx-pl-4 contrast-more:hx-border-current contrast-more:dark:hx-border-current hx-border-yellow-100 hx-bg-yellow-50 hx-text-yellow-900 dark:hx-border-yellow-200/30 dark:hx-bg-yellow-700/30 dark:hx-text-yellow-200"><div class="ltr:hx-pl-3 ltr:hx-pr-2 rtl:hx-pr-3 rtl:hx-pl-2"><div class="hx-select-none hx-text-xl" style="font-family:apple color emoji,segoe ui emoji,segoe ui symbol">⚠️</div></div><div class="hx-w-full hx-min-w-0 hx-leading-7"><div class="hx-mt-6 hx-leading-7 first:hx-mt-0">Avoid auto-merging dependency updates without human review. Compromised maintainer accounts often push malicious code as patch releases specifically because they receive less scrutiny. Automated tests won&rsquo;t catch intentional backdoors.</div></div></div><ol><li><strong>Review changelogs and release notes</strong>: Before approving any dependency update, check the changelog for breaking changes, security fixes, and new features. Understand what you&rsquo;re bringing into your codebase.</li><li><strong>Verify maintainer identity</strong>: Check the maintainer&rsquo;s identity and history. Look for recent ownership transfers, new maintainers, or changes in publishing patterns—all potential indicators of account compromise.</li><li><strong>Inspect the diff</strong>: Review the actual code changes between versions, especially for dependencies with broad access to your system.</li><li><strong>Don&rsquo;t trust semver for security decisions</strong>: Semantic versioning indicates <em>intended</em> API compatibility, not security risk. A &ldquo;patch&rdquo; release can contain arbitrary code changes. Attackers specifically target patch releases because organizations often fast-track them with less scrutiny.</li><li><strong>Group updates for efficient review</strong>: Instead of reviewing updates one-by-one, batch dependency updates into scheduled review sessions. This allows focused attention without creating bottlenecks.</li><li><strong>Document decisions</strong>: Record why specific versions were approved or rejected. This creates an audit trail and helps future reviewers.</li></ol><h2>Trade-offs and considerations<span class="hx-absolute -hx-mt-20" id=trade-offs-and-considerations></span>
<a href=#trade-offs-and-considerations class=subheading-anchor aria-label="Permalink for this section"></a></h2><h3>Balancing security with development velocity<span class="hx-absolute -hx-mt-20" id=balancing-security-with-development-velocity></span>
<a href=#balancing-security-with-development-velocity class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>The most secure approach (reviewing every dependency change manually and disabling all automation) is impractical for most organizations. The key is finding the right balance:</p><p><strong>For high-security environments:</strong></p><ul><li>Disable lifecycle scripts with no exceptions except for explicitly approved packages</li><li>Require manual review of all dependency updates</li><li>Validate package attestations and block on missing attestations</li><li>Use allow-lists of approved dependencies</li><li>Mirror packages through private registries (GitHub Packages, Artifactory, Nexus) for additional approval controls</li></ul><p><strong>For balanced security:</strong></p><ul><li>Disable lifecycle scripts by default with documented exceptions</li><li>Require human review for all dependency updates (batch for efficiency, not reduced scrutiny)</li><li>Validate attestations when available but don&rsquo;t block on absence</li><li>Use dependency review action and code scanning as automated safety nets</li></ul><h3>Common challenges<span class="hx-absolute -hx-mt-20" id=common-challenges></span>
<a href=#common-challenges class=subheading-anchor aria-label="Permalink for this section"></a></h3><ul><li><strong>Packages requiring lifecycle scripts</strong>: Some packages (like <code>node-gyp</code> for native extensions) legitimately need scripts. Create a documented exception list and use <code>npm rebuild &lt;package></code> selectively after installation.</li><li><strong>Alert fatigue</strong>: Dependabot can generate many alerts. Use <a href=https://docs.github.com/enterprise-cloud@latest/code-security/dependabot/dependabot-auto-triage-rules/about-dependabot-auto-triage-rules target=_blank rel=noopener>auto-triage rules</a> to dismiss low-risk alerts and prioritize what matters.</li><li><strong>Transitive dependencies</strong>: You don&rsquo;t control dependencies of your dependencies. Use <code>npm audit</code>, Dependabot, dependency review, and code scanning to gain visibility. Consider replacing direct dependencies that bring in vulnerable transitives.</li><li><strong>Attestations not universally available</strong>: Not all packages support attestations yet. Use attestation availability as one factor in dependency selection and gradually work toward full coverage.</li><li><strong>Keeping lockfiles current</strong>: Lockfiles prevent unexpected updates but can become stale. Regularly update dependencies through Dependabot or scheduled audits to ensure security patches aren&rsquo;t missed while maintaining reproducible builds.</li><li><strong>Breaking changes in security updates</strong>: Security updates sometimes include breaking changes that require code modifications. Establish separate processes for security updates (expedited) vs. feature updates (standard review), and allocate time for security debt remediation.</li><li><strong>Workflow security risks</strong>: The <code>pull_request_target</code> trigger runs with elevated permissions and access to secrets, even for pull requests from forks. Prefer the regular <code>pull_request</code> trigger, define least-privilege workflow permissions, and enable <a href=https://docs.github.com/enterprise-cloud@latest/code-security/code-scanning/introduction-to-code-scanning/about-code-scanning target=_blank rel=noopener>CodeQL workflow analysis</a> to detect vulnerabilities. See the <a href=https://github.blog/news-insights/product-news/whats-coming-to-our-github-actions-2026-security-roadmap/ target=_blank rel=noopener>GitHub Actions 2026 security roadmap</a> for upcoming capabilities addressing these risks.</li></ul><h2>Seeking further assistance<span class="hx-absolute -hx-mt-20" id=seeking-further-assistance></span>
