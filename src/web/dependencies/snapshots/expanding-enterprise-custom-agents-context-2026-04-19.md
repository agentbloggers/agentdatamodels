hx-whitespace-nowrap"><div>March 11, 2026</div></div></div><h2>Scenario overview<span class="hx-absolute -hx-mt-20" id=scenario-overview></span>
<a href=#scenario-overview class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>GitHub Enterprise Custom Agents enable organizations to create specialized coding agents tailored to their development workflows, coding standards, and internal processes. These agents are configured at the enterprise level and defined by markdown files stored in the <code>.github-private</code> repository of a configured organization, providing context and instructions to guide the Copilot Coding Agent&rsquo;s behavior.</p><p>However, the defining markdown file has a <strong>30,000 character limit</strong>, which can be restrictive when providing comprehensive context for complex enterprise environments. When a custom agent is invoked through the GitHub UI, only this singular markdown file is passed as context—all other files in the repository remain inaccessible to the agent during execution.</p><p>This limitation becomes particularly challenging for organizations that need to provide extensive guidance on coding patterns, architectural standards, security requirements, and compliance policies. The challenge is further complicated by authentication and access control requirements, especially in GitHub Enterprise Cloud with Managed Users (EMU) and Data Residency environments where secure access to private repositories is essential.</p><p>This article provides a prescriptive approach to expanding the available context beyond the single markdown file by leveraging the Model Context Protocol (MCP) and GitHub&rsquo;s built-in MCP server.</p><h2>Key design strategies and checklist<span class="hx-absolute -hx-mt-20" id=key-design-strategies-and-checklist></span>
<a href=#key-design-strategies-and-checklist class=subheading-anchor aria-label="Permalink for this section"></a></h2><h3>Design strategies<span class="hx-absolute -hx-mt-20" id=design-strategies></span>
<a href=#design-strategies class=subheading-anchor aria-label="Permalink for this section"></a></h3><p><strong>Centralized knowledge management.</strong> Store additional context files in a structured knowledge directory within the <code>.github-private</code> repository. This keeps all custom agent resources in a single, version-controlled location that administrators can manage through standard Git workflows.</p><p><strong>Dynamic context loading.</strong> Instruct custom agents to fetch additional context files at runtime using the GitHub MCP server. This approach allows agents to access expanded context without hitting the single-file character limit, and enables updates to knowledge files without modifying the agent definition.</p><p><strong>Per-repository authentication.</strong> Configure repository-specific access credentials using Copilot environment secrets. This provides fine-grained control over which repositories can access expanded context while maintaining security boundaries.</p><p><strong>Structured content organization.</strong> Organize knowledge files by domain, topic, or concern (e.g., security policies, Docker patterns, CI/CD best practices). This modular approach makes it easier to maintain and update specific areas of guidance as organizational standards evolve.</p><h3>Implementation checklist<span class="hx-absolute -hx-mt-20" id=implementation-checklist></span>
<a href=#implementation-checklist class=subheading-anchor aria-label="Permalink for this section"></a></h3><ul><li><input disabled type=checkbox> Create a <code>knowledge</code> directory in the <code>.github-private</code> repository</li><li><input disabled type=checkbox> Organize knowledge files using descriptive filenames and subdirectories</li><li><input disabled type=checkbox> Update custom agent markdown to include instructions for fetching knowledge files</li><li><input disabled type=checkbox> Generate a Personal Access Token (PAT) with <code>repo</code> scope for the <code>.github-private</code> repository</li><li><input disabled type=checkbox> Configure the <code>copilot</code> environment in target repositories</li><li><input disabled type=checkbox> Add the <code>COPILOT_MCP_GITHUB_PERSONAL_ACCESS_TOKEN</code> secret to each repository environment</li><li><input disabled type=checkbox> Test the agent to verify it successfully fetches and uses expanded context</li><li><input disabled type=checkbox> Document the knowledge file structure and maintenance procedures for your team</li></ul><h2>Assumptions and preconditions<span class="hx-absolute -hx-mt-20" id=assumptions-and-preconditions></span>
<a href=#assumptions-and-preconditions class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>Before implementing this solution, the following must be in place:</p><ul><li><strong>GitHub Enterprise Custom Agents enabled.</strong> Your organization has <a href=https://docs.github.com/enterprise-cloud@latest/copilot/how-tos/administer-copilot/manage-for-enterprise/manage-agents/prepare-for-custom-agents target=_blank rel=noopener>GitHub Enterprise Custom Agents</a> configured and the <code>.github-private</code> repository created.</li><li><strong>Model Context Protocol (MCP) configured.</strong> The <a href=https://docs.github.com/enterprise-cloud@latest/copilot/concepts/agents/coding-agent/mcp-and-coding-agent target=_blank rel=noopener>Model Context Protocol</a> is enabled in your GitHub Enterprise settings, providing access to the GitHub MCP server.</li><li><strong>Administrative access.</strong> You have admin access to the <code>.github-private</code> repository and permissions to configure environment secrets in target repositories.</li><li><strong>GitHub Enterprise Cloud.</strong> This solution is designed for GitHub Enterprise Cloud, including EMU and Data Residency environments. It leverages features specific to these platforms.</li><li><strong>Understanding of custom agents.</strong> Team members responsible for implementing this solution understand how custom agents are defined and invoked.</li></ul><h2>Recommended deployment<span class="hx-absolute -hx-mt-20" id=recommended-deployment></span>

<a href=#additional-solution-detail-and-trade-offs-to-consider class=subheading-anchor aria-label="Permalink for this section"></a></h2><h3>Why this approach is recommended<span class="hx-absolute -hx-mt-20" id=why-this-approach-is-recommended></span>
<a href=#why-this-approach-is-recommended class=subheading-anchor aria-label="Permalink for this section"></a></h3><p><strong>Overcomes character limits.</strong> The primary benefit is bypassing the 30,000 character limitation of the agent definition file. Organizations can provide comprehensive guidance across dozens or hundreds of separate knowledge files, each focused on specific domains.</p><p><strong>Enables dynamic updates.</strong> Knowledge files can be updated independently of agent definitions. When you update a security policy or coding standard in the knowledge base, all agents that reference it immediately use the updated guidance—no need to modify agent markdown files.</p><p><strong>Maintains version control.</strong> Storing knowledge files in the <code>.github-private</code> repository provides full Git version control. Teams can review changes through pull requests, track evolution over time, and revert if needed.</p><p><strong>Centralizes organizational knowledge.</strong> A single knowledge directory becomes the source of truth for organizational standards, patterns, and policies. Multiple custom agents can reference the same knowledge files, ensuring consistency across different agent specializations.</p><h3>Trade-offs and considerations<span class="hx-absolute -hx-mt-20" id=trade-offs-and-considerations></span>
<a href=#trade-offs-and-considerations class=subheading-anchor aria-label="Permalink for this section"></a></h3><p><strong>Authentication complexity.</strong> Each repository requires individual configuration of the environment secret. <a href=#alternative-approaches class=subheading-anchor aria-label="Permalink for this section"></a></h3><p><strong>Inline all guidance in agent markdown.</strong> For smaller organizations or simpler use cases, keeping all guidance within the 30,000 character limit may be sufficient. This eliminates authentication complexity and runtime latency.</p><p><strong>Pros:</strong></p><ul><li>No additional configuration required</li><li>Faster agent startup (no fetching needed)</li><li>Simpler to understand and maintain</li></ul><p><strong>Cons:</strong></p><ul><li>Limited to 30,000 characters total</li><li>Must edit agent file to update any guidance</li><li>Difficult to share guidance across multiple agents</li></ul><p><strong>Use external documentation systems.</strong> Store organizational standards in external wikis, Confluence, or documentation platforms and have agents reference URLs.</p><p><strong>Pros:</strong></p><ul><li>Leverages existing documentation infrastructure</li><li>Can include rich media, diagrams, and interactive content</li><li>May already be maintained by technical writing teams</li></ul><p><strong>Cons:</strong></p><ul><li>Agents cannot directly access content from URLs (requires summarizing in markdown)</li><li>External systems may not be accessible during agent execution</li><li>Version control and change tracking are external to the agent workflow</li><li>Authentication to external systems adds complexity</li></ul><p><strong>Public documentation in separate repository.</strong> For guidance that isn&rsquo;t sensitive, create a public or internal repository with knowledge files.</p><p><strong>Pros:</strong></p><ul><li>No authentication configuration needed for public repositories</li><li>Can be shared across organizations or with partners</li><li>Easier to manage access for external contributors</li></ul><p><strong>Cons:</strong></p><ul><li>Only suitable for non-sensitive guidance</li><li>Requires managing a separate repository</li><li>Still requires updating agents to reference the correct repository</li></ul><h3>When not to use this approach<span class="hx-absolute -hx-mt-20" id=when-not-to-use-this-approach></span>
<a href=#when-not-to-use-this-approach class=subheading-anchor aria-label="Permalink for this section"></a></h3><p><strong>Small, simple use cases.</strong> If your organizational guidance fits comfortably within the 30,000 character limit and doesn&rsquo;t change frequently, the added complexity of expanded context may not be worthwhile.</p><p><strong>Highly dynamic guidance.</strong> If guidance changes multiple times per day based on external factors (like rotating API keys or dynamic allow-lists), consider integrating with a configuration service or API rather than static markdown files.</p><p><strong>Cross-organization sharing.</strong> If you need to share custom agents across multiple GitHub organizations, managing authentication and knowledge access becomes significantly more complex. Consider using organization-independent guidance or implementing a centralized knowledge service.</p><h3>Best practices for knowledge management<span class="hx-absolute -hx-mt-20" id=best-practices-for-knowledge-management></span>
