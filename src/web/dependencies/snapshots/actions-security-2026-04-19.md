2024</div><div>|</div><div>Updated <time datetime=2026-02-02T23:51:40.000Z>February 2, 2026</time></div></div></div><h2>Scenario overview<span class="hx-absolute -hx-mt-20" id=scenario-overview></span>
<a href=#scenario-overview class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>Continuous integration and continuous delivery (CI/CD) are essential components of modern software development. GitHub Actions is a powerful tool that enables developers to automate repetitive tasks and reduce the risk of human error in manual workflows.</p><p>However, CI/CD tools inherently provide remote code execution as a service, making them a prime attack vector for malicious actors. Securing GitHub Actions workflows is critical to prevent unauthorized access to the codebase and protect organizations from potential security breaches.</p><h2>Key design strategies<span class="hx-absolute -hx-mt-20" id=key-design-strategies></span>
<a href=#key-design-strategies class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>To secure GitHub Actions workflows, consider the following strategies:</p><ol><li><strong>Use OpenID Connect (OIDC) for authentication</strong>: Establish authentication between GitHub Actions and external systems or cloud providers using OIDC. Use short-lived tokens whenever possible to access resources, and avoid storing long-lived credentials as secrets.</li><li><strong>Configure repository rules</strong>: Implement repository rulesets to enforce security policies and prevent unauthorized or malicious changes.</li><li><strong>Implement least privilege for workflow permissions</strong>: Restrict workflow and job permissions to the minimum required. Remove workflow-level permissions and define permissions on individual jobs rather than at the workflow level for finer-grained control.</li><li><strong>Use Dependabot to protect the supply chain</strong>: Enable Dependabot alerts and security updates to identify and remediate vulnerable dependencies in workflows. Enable version updates to regularly review and update dependencies.</li><li><strong>Pin versions of actions</strong>: Pin actions to a specific commit hash to prevent breaking changes or vulnerabilities in newer versions. Enforce via the allowed actions and reusable workflows policy at the enterprise, organization, or repository level.</li><li><strong>Avoid actions with mutable dependencies</strong>: Do not use actions that include mutable dependencies (e.g. <code>latest</code>) or pull in external binaries without verification, as they introduce supply chain risks.</li><li><strong>Avoid workflow injection</strong>: Sanitize user input and avoid using expression values in sensitive contexts (such as <code>run</code> steps) to prevent injection attacks.</li><li><strong>Avoid <code>pull_request_target</code></strong>: This event runs workflows in the base repository context with elevated permissions. This can enable malicious execution using pull requests from forks.</li><li><strong>Secure <code>workflow_run</code> workflows</strong>: Treat all artifacts, code, and data from triggering workflows as untrusted. Use <a href=https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#limiting-your-workflow-to-run-based-on-branches target=_blank rel=noopener>branch filters</a> and validate all inputs.</li><li><strong>Use <code>head.sha</code> instead of <code>head.ref</code></strong>: Where possible, reference by commit SHA instead of a user-provided branch name or tag (ref), especially in sensitive contexts (such as <code>run</code> steps). If require, use environment variable to store <code>head.ref</code> and reference it to prevent injection attack.</li><li><strong>Use caution with public repositories</strong>: Anyone can suggest changes to public repositories. Review workflow triggers, and never use self-hosted runners with public repositories.</li><li><strong>Restrict allowed actions</strong>: Use the <a href=https://docs.github.com/en/enterprise-cloud@latest/admin/enforcing-policies/enforcing-policies-for-your-enterprise/enforcing-policies-for-github-actions-in-your-enterprise#controlling-access-to-public-actions-and-reusable-workflows target=_blank rel=noopener><em>Allow enterprise, and select non-enterprise, actions and reusable workflows</em></a> setting to control which actions can run.</li></ol><h2>Assumptions and preconditions<span class="hx-absolute -hx-mt-20" id=assumptions-and-preconditions></span>
<a href=#assumptions-and-preconditions class=subheading-anchor aria-label="Permalink for this section"></a></h2><p>This article assumes readers are familiar with <a href=https://docs.github.com/en/enterprise-cloud@latest/actions/about-github-actions/understanding-github-actions target=_blank rel=noopener>GitHub Actions</a> and have experience creating and managing workflows. It also assumes a basic understanding of security best practices and concepts such as authentication, authorization, and OIDC.</p><h2>Recommended implementation<span class="hx-absolute -hx-mt-20" id=recommended-implementation></span>
<a href=#recommended-implementation class=subheading-anchor aria-label="Permalink for this section"></a></h2><h3>Use OpenID Connect (OIDC) for authentication<span class="hx-absolute -hx-mt-20" id=use-openid-connect-oidc-for-authentication></span>
<a href=#use-openid-connect-oidc-for-authentication class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>CI/CD platforms like GitHub Actions often require access to sensitive resources such as source code repositories, build artifacts, and deployment environments. To ensure that only authorized users and services can access these resources, <a href=https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/about-security-hardening-with-openid-connect target=_blank rel=noopener>use OpenID Connect (OIDC) for authentication</a>.</p><p>OIDC eliminates the need for long-lived credentials in Actions secrets, reducing the risk of secret exfiltration. By establishing trust between GitHub Actions and a service that supports OIDC, attributes like organization, repository, workflow, or user can be used as conditions to approve or deny access.</p><h4>Configuring trust relationships with specific claims<span class="hx-absolute -hx-mt-20" id=configuring-trust-relationships-with-specific-claims></span>
<a href=#configuring-trust-relationships-with-specific-claims class=subheading-anchor aria-label="Permalink for this section"></a></h4><p>When <a href=https://docs.github.com/en/actions/reference/security/oidc#oidc-claims-used-to-define-trust-conditions-on-cloud-roles target=_blank rel=noopener>configuring OIDC trust relationships with cloud providers</a> or compliant services, specify granular claims to restrict access to trusted conditions. For example:</p><ul><li><strong><code>sub</code> claim</strong>: The primary OIDC subject identifier, uniquely representing the repository that requested the token. Use this claim to restrict access to specific repositories and environments. Prefer an exact match on a complete claim instead of wildcard matches.</li><li><strong><code>job_workflow_ref</code> claim</strong>: Specifies the exact workflow file path and commit SHA. Note that only a limited number of cloud providers support this custom claim (e.g. <a href="https://learn.microsoft.com/en-us/entra/workload-id/workload-identities-flexible-federated-identity-credentials?tabs=github" target=_blank rel=noopener>Azure</a>).</li></ul><p>Define the most granular trust conditions wherever possible to prevent unauthorized access, even from legitimate repositories. <a href=https://docs.github.com/en/enterprise-cloud@latest/actions/reference/security/oidc#customizing-the-token-claims target=_blank rel=noopener>Customize the <code>sub</code> claim</a> when the cloud provider&rsquo;s OIDC implementation does not support matching <strong>custom claims</strong> or you need immutable identifiers in the <code>sub</code>.</p><ul><li>Prefer <strong>immutable identifiers</strong> (e.g., <code>repository_owner_id:12345:repository_id:67890</code>) over mutable ones (e.g., <code>repo:github/some-repo</code>).</li></ul><h4>Scaling with reusable workflows<span class="hx-absolute -hx-mt-20" id=scaling-with-reusable-workflows></span>
<a href=#scaling-with-reusable-workflows class=subheading-anchor aria-label="Permalink for this section"></a></h4><p>OIDC can also <a href=https://docs.github.com/en/actions/security-for-github-actions/security-hardening-your-deployments/using-openid-connect-with-reusable-workflows target=_blank rel=noopener>secure reusable workflows</a> across multiple organizations and repositories. Use <code>job_workflow_ref</code> to ensure only approved workflows access sensitive resources.</p><h3>Configure repository rules<span class="hx-absolute -hx-mt-20" id=configure-repository-rules></span>
<a href=#configure-repository-rules class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Repository rulesets provide a strong defensive layer that complements workflow-level security measures. Consider these rules:</p><ul><li><a href=https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-a-pull-request-before-merging target=_blank rel=noopener>Require pull requests before merging</a>: Enforce human review to detect malicious changes. For example, require human review and at least two reviewers to merge to the default branch.</li><li><a href=https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-status-checks-to-pass-before-merging target=_blank rel=noopener>Require status checks to pass before merging</a>: Ensure automated validation checks pass before merging.</li><li><a href=https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-code-scanning-results target=_blank rel=noopener>Require code scanning results</a>: Identify security vulnerabilities before merge.</li><li><a href=https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets#require-signed-commits target=_blank rel=noopener>Require signed commits</a>: Ensure all commits are signed to prove who authored them and that they haven&rsquo;t been modified.</li><li>Restrict bypass permissions: Limit bypass capabilities to emergencies and monitor via audit logs.</li></ul><h3>Implement least privilege for workflow permissions<span class="hx-absolute -hx-mt-20" id=implement-least-privilege-for-workflow-permissions></span>

These default permissions can be configured as either <strong>permissive</strong> or <strong>restricted</strong> at the <a href=https://docs.github.com/en/enterprise-cloud@latest/organizations/managing-organization-settings/disabling-or-limiting-github-actions-for-your-organization#setting-the-permissions-of-the-github_token-for-your-organization target=_blank rel=noopener>organization level</a> or at the <a href=https://docs.github.com/en/enterprise-cloud@latest/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#setting-the-permissions-of-the-github_token-for-your-repository target=_blank rel=noopener>repository level</a>.</p><p>Set the organization-level or repository-level default to <strong>restricted</strong> (read-only). By enabling Dependabot, teams can ensure that:</p><ul><li>Actions used in workflows are up to date</li><li>Container images, packages, and other dependencies in the repository are secure</li><li>The supply chain is monitored for vulnerabilities</li></ul><div class="hx-overflow-x-auto hx-mt-6 hx-flex hx-rounded-lg hx-border hx-py-2 ltr:hx-pr-4 rtl:hx-pl-4 contrast-more:hx-border-current contrast-more:dark:hx-border-current hx-border-yellow-100 hx-bg-yellow-50 hx-text-yellow-900 dark:hx-border-yellow-200/30 dark:hx-bg-yellow-700/30 dark:hx-text-yellow-200"><div class="ltr:hx-pl-3 ltr:hx-pr-2 rtl:hx-pr-3 rtl:hx-pl-2"><div class="hx-select-none hx-text-xl" style="font-family:apple color emoji,segoe ui emoji,segoe ui symbol">⚠️</div></div><div class="hx-w-full hx-min-w-0 hx-leading-7"><div class="hx-mt-6 hx-leading-7 first:hx-mt-0">Dependabot will only create Dependabot alerts for vulnerable GitHub Actions that use semantic versioning. Actions pinned to SHAs will only receive version updates, not security alerts. For more information, see <a href=https://docs.github.com/en/code-security/dependabot/dependabot-alerts/about-dependabot-alerts target=_blank rel=noopener>About Dependabot alerts</a>.</div></div></div><h3>Pin versions of actions<span class="hx-absolute -hx-mt-20" id=pin-versions-of-actions></span>
<a href=#pin-versions-of-actions class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>When using third-party actions in workflows, pin them to an immutable reference (a commit SHA or the tag from an immutable release) to avoid breaking changes, security vulnerabilities, and supply chain attacks from maliciously modified tags.</p><p>Pinning an action to a full-length commit SHA is the most reliable way to use an immutable version of an action. While GitHub offers immutable tags as an alternative, this feature can be disabled by repository owners. Pinning to a specific SHA mitigates the risk of a bad actor changing a tag to point to malicious code. When selecting a SHA, verify it comes from the action&rsquo;s official repository and not a fork. <strong>Use SHAs from tagged releases so Dependabot version updates can suggest updates</strong>. If a tag is used from an immutable release, always verify a new version is also immutable.</p><p>To pin the version of an action to a commit SHA, specify the commit hash in the <code>uses</code> field of the workflow file. Tie the commit SHA directly to a tag version (not an arbitrary commit on the default branch) and add a comment noting the version. For example:</p><div class="hextra-code-block hx-relative hx-mt-6 first:hx-mt-0 hx-group/code"><div><div class=highlight><pre tabindex=0 class=chroma><code class=language-yaml data-lang=yaml><span class=line><span class=cl>- <span class=nt>uses</span><span class=p>:</span><span class=w> </span><span class=l>actions/checkout@692973e3d937129bcbf40652eb9f2f61becf3332</span><span class=w> </span><span class=c># v4.1.7</span></span></span></code></pre></div></div><div class="hextra-code-copy-btn-container hx-opacity-0 hx-transition group-hover/code:hx-opacity-100 hx-flex hx-gap-1 hx-absolute hx-m-[11px] hx-right-0 hx-top-0"><button class="hextra-code-copy-btn hx-group/copybtn hx-transition-all active:hx-opacity-50 hx-bg-primary-700/5 hx-border hx-border-black/5 hx-text-gray-600 hover:hx-text-gray-900 hx-rounded-md hx-p-1.5 dark:hx-bg-primary-300/10 dark:hx-border-white/10 dark:hx-text-gray-400 dark:hover:hx-text-gray-50" title="Copy code"><div class="copy-icon group-[.copied]/copybtn:hx-hidden hx-pointer-events-none hx-h-4 hx-w-4"></div><div class="success-icon hx-hidden group-[.copied]/copybtn:hx-block hx-pointer-events-none hx-h-4 hx-w-4"></div></button></div></div><p>Including the version number in a comment helps teams track versions and makes it easier to identify outdated actions.</p><p>Security administrators can enforce policies requiring all GitHub Actions workflows and reusable workflow references to be pinned to full-length commit SHAs. This enforcement is available at the enterprise, organization, and repository levels and can be enabled via a dedicated checkbox in the allowed actions and reusable workflows policy settings.</p><h3>Avoid actions with mutable dependencies<span class="hx-absolute -hx-mt-20" id=avoid-actions-with-mutable-dependencies></span>
<a href=#avoid-actions-with-mutable-dependencies class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Some actions include mutable dependencies or pull in code from external sources without verification. These actions remain mutable even after pinning to a specific commit hash, since they include components that can change behavior without altering the action’s source code. Using mutable actions dependencies introduces security risks and makes workflows vulnerable to supply chain attacks.</p><p>To avoid using actions with mutable dependencies, review actions source code and ensure they do not include elements such as unpinned container images, unpinned composite actions, or scripts that download code from external sources without verification.</p><h3>Avoid workflow injection<span class="hx-absolute -hx-mt-20" id=avoid-workflow-injection></span>
<a href=#avoid-workflow-injection class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Avoid inserting untrusted input into any executable context such as <code>run:</code> blocks using expressions. Values like issue titles, PR bodies, and branch names can be manipulated by attackers to inject malicious commands. Use environment variables to safely incorporate user input.</p><p>For more details on the risk of workflow script injections and mitigation strategies, refer to <a href=https://docs.github.com/en/enterprise-cloud@latest/actions/security-for-github-actions/security-guides/security-hardening-for-github-actions#understanding-the-risk-of-script-injections target=_blank rel=noopener>GitHub Docs</a>.</p><h3>Avoid <code>pull_request_target</code><span class="hx-absolute -hx-mt-20" id=avoid-pull_request_target></span>
<a href=#avoid-pull_request_target class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>The <code>pull_request_target</code> event is a privileged workflow trigger that should be used with extreme caution. Unlike <code>pull_request</code>, which runs in the context of the pull request branch with read-only permissions and no access to secrets, <code>pull_request_target</code> runs in the context of the base repository with full access to repository secrets and write permissions.</p><p>The risk arises when a workflow using <code>pull_request_target</code> explicitly checks out code from the pull request and executes it. Because the workflow runs with base repository privileges, this combination allows untrusted code to execute with elevated permissions. This scenario is known as a <a href=https://securitylab.github.com/resources/github-actions-preventing-pwn-requests/ target=_blank rel=noopener>&ldquo;pwn request&rdquo;</a>.</p><h4>When <code>pull_request_target</code> is appropriate<span class="hx-absolute -hx-mt-20" id=when-pull_request_target-is-appropriate></span>
<a href=#when-pull_request_target-is-appropriate class=subheading-anchor aria-label="Permalink for this section"></a></h4><p>The <code>pull_request_target</code> trigger is designed for specific use cases where elevated permissions are required to interact with pull requests from forks, such as:</p><ul><li>Posting comments or labels on pull requests</li><li>Updating pull request status or metadata</li></ul><p>Avoid this trigger for public repositories, and be cautious in implementing this trigger for internal repositories.</p><h3>Secure <code>workflow_run</code> workflows<span class="hx-absolute -hx-mt-20" id=secure-workflow_run-workflows></span>
<a href=#secure-workflow_run-workflows class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>The <code>workflow_run</code> event executes workflows after another workflow completes. While useful for privileged operations after validation, it carries security risks. Attackers can modify triggering workflows in pull requests, which then trigger existing <code>workflow_run</code> workflows with elevated permissions. Additionally, malicious artifacts uploaded by unprivileged workflows can poison privileged workflows that consume them.</p><p>When implementing <code>workflow_run</code> workflows:</p><ul><li>Use branch filters to limit where workflows can be triggered</li><li>Verify the event origin with <code>github.event.workflow_run.event != 'pull_request'</code></li><li>Treat all artifacts as untrusted and validate contents before use</li><li>Download artifacts to temporary directories (e.g., <code>$RUNNER_TEMP</code>) to prevent workspace pollution</li><li>Avoid defining global environment variables in <code>$GITHUB_ENV</code> from untrusted data</li></ul><h3>Use caution with public repositories<span class="hx-absolute -hx-mt-20" id=use-caution-with-public-repositories></span>
<a href=#use-caution-with-public-repositories class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Public repositories enable open-source collaboration but introduce significant security considerations. The most critical risk is using self-hosted runners with public repositories.</p><div class="hx-overflow-x-auto hx-mt-6 hx-flex hx-rounded-lg hx-border hx-py-2 ltr:hx-pr-4 rtl:hx-pl-4 contrast-more:hx-border-current contrast-more:dark:hx-border-current hx-border-yellow-100 hx-bg-yellow-50 hx-text-yellow-900 dark:hx-border-yellow-200/30 dark:hx-bg-yellow-700/30 dark:hx-text-yellow-200"><div class="ltr:hx-pl-3 ltr:hx-pr-2 rtl:hx-pr-3 rtl:hx-pl-2"><div class="hx-select-none hx-text-xl" style="font-family:apple color emoji,segoe ui emoji,segoe ui symbol">⚠️</div></div><div class="hx-w-full hx-min-w-0 hx-leading-7"><div class="hx-mt-6 hx-leading-7 first:hx-mt-0"><p>Avoid use self-hosted runners with public repositories. When a public repository is configured to use self-hosted runners, anyone who can create a fork can potentially run dangerous code on the self-hosted runner machine by creating a pull request that executes code in a workflow. This can lead to:</p><ul><li>Malicious programs running on the machine</li><li>Escaping the machine&rsquo;s runner sandbox</li><li>Exposing access to the machine&rsquo;s network environment</li><li>Persisting unwanted or dangerous data on the machine</li><li>Poisoning caches that could affect other repositories or workflows</li></ul></div></div></div><p>If allowing pull requests from forks, consider enabling &ldquo;<a href=https://docs.github.com/en/repositories/managing-your-repositorys-settings-and-features/enabling-features-for-your-repository/managing-github-actions-settings-for-a-repository#controlling-changes-from-forks-to-workflows-in-public-repositories target=_blank rel=noopener>require approval for all outside collaborators</a>&rdquo; to require approval before workflows run on fork PRs.</p><p>Even ephemeral self-hosted runners carry risks in public repository contexts, as attackers can exploit the window between job start and completion, or leverage shared resources like caches.</p><div class="hx-overflow-x-auto hx-mt-6 hx-flex hx-rounded-lg hx-border hx-py-2 ltr:hx-pr-4 rtl:hx-pl-4 contrast-more:hx-border-current contrast-more:dark:hx-border-current hx-border-blue-200 hx-bg-blue-100 hx-text-blue-900 dark:hx-border-blue-200/30 dark:hx-bg-blue-900/30 dark:hx-text-blue-200"><div class="ltr:hx-pl-3 ltr:hx-pr-2 rtl:hx-pr-3 rtl:hx-pl-2"><div class="hx-select-none hx-text-xl" style="font-family:apple color emoji,segoe ui emoji,segoe ui symbol">ℹ️</div></div><div class="hx-w-full hx-min-w-0 hx-leading-7"><div class="hx-mt-6 hx-leading-7 first:hx-mt-0">GitHub-hosted runners are network isolated by default. They can make outbound calls but do not have access to other runners. Each GitHub-hosted runner is a clean isolated virtual machine that is destroyed at the end of the job execution.</div></div></div><h3>Restrict allowed actions<span class="hx-absolute -hx-mt-20" id=restrict-allowed-actions></span>
<a href=#restrict-allowed-actions class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>The <a href=https://docs.github.com/en/enterprise-cloud@latest/admin/enforcing-policies/enforcing-policies-for-your-enterprise/enforcing-policies-for-github-actions-in-your-enterprise#allowing-select-actions-and-reusable-workflows-to-run target=_blank rel=noopener>allowed actions and reusable workflows setting</a> controls which actions can run (or not run) in your organization or enterprise. This provides centralized governance and makes it easy to respond to compromised actions without searching across repositories.</p><p>Consider defining the list of allowed actions using policy as code (e.g., via Terraform or the REST API) to establish a request/approval process, track changes for audit purposes, and improve visibility into which actions are allowed.</p><h2>Additional solution detail and trade-offs to consider<span class="hx-absolute -hx-mt-20" id=additional-solution-detail-and-trade-offs-to-consider></span>
<a href=#additional-solution-detail-and-trade-offs-to-consider class=subheading-anchor aria-label="Permalink for this section"></a></h2><h3>Pinning actions based on a version tag<span class="hx-absolute -hx-mt-20" id=pinning-actions-based-on-a-version-tag></span>
<a href=#pinning-actions-based-on-a-version-tag class=subheading-anchor aria-label="Permalink for this section"></a></h3><p>Although pinning to a commit hash is the most secure option, specifying a tag is more convenient and widely used.
